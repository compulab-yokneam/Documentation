# CompuLab U-Boot: DRAM Configurations, SPL Sizing

## 1. SPL size issue

After additional LPDDR4 timing data were added to support the combined `D2/D4` DRAM configuration, the CompuLab U-Boot SPL exceeded the configured SRAM limit.

The linker reported:

```text
u-boot-spl section `.data' will not fit in region `.sram'
region `.sram' overflowed by [verify the reported byte count] bytes
```

One proposed solution is to increase the maximum SPL size and padding:

```text
CONFIG_SPL_MAX_SIZE=0x2C000
CONFIG_SPL_PAD_TO=0x2C000
```

The resulting `flash.bin` boots successfully when it is generated using the U-Boot `binman` flow.

However, in our testing, the image generated by the Yocto `imx-mkimage` flow does not boot correctly when the enlarged SPL is used. The device hangs during LPDDR4 initialization and training in SPL.

## 2. Available solutions

### Solution 1: Separate D2 and D4 configurations

This solution is implemented in the released software.

The combined `D2/D4` timing configuration was split into separate `D2` and `D4` configurations. Consequently, each build includes only the timing data required for the selected DRAM variant. This reduces the SPL size and allows the default `0x26000` SPL limit to be retained.

**U-Boot source:** the referenced revision contains separate `d2.config`, `d4.config`, and `d1d8.config` configuration fragments. ([GitHub][1])

**Yocto meta-layer:** the `iot-gate-imx8plus-r3.2` branch. ([GitHub][5])

**U-Boot recipe:** the recipe independently selects the `d2`, `d4`, or `d1d8` configuration according to `DRAM_CONF`. 

### Solution 2: Combined DRAM configurations with an enlarged SPL

This solution is currently available in the development branches.

It retains the combined `D2/D4` and `D1/D8` timing configurations and increases the SPL size and padding to `0x2C000`.

**U-Boot source:** the `u-boot-compulab_v2023.04-d1d8_d2d4` branch. The branch provides the combined `d2d4` and `d1d8` configuration fragments. ([GitHub][2])

**Yocto meta-layer:** the `wrynose-6.18.20-2.0.0` development branch. ([GitHub][6])

The corresponding U-Boot recipe includes `spl_size.cfg` and supports both combined DRAM configurations, including `d1d8` and `d2d4`. 

The default machine configuration is:

```text
DRAM_CONF ??= "d2d4"
```

The enlarged SPL configuration is:

```text
CONFIG_SPL_MAX_SIZE=0x2C000
CONFIG_SPL_PAD_TO=0x2C000
```

# Mender and Linux DTB handling

> As far as I can tell, U-Boot finds the DTB in the boot partition. However, because the boot partition is not part of Mender’s A/B slots, an OTA update does not result in the new DTB being loaded. Am I missing something in how this should be configured?

The Linux DTB passed to the kernel is not part of the U-Boot bootloader itself. In a Mender A/B configuration, the Linux kernel and its matching DTB should normally be stored together under `/boot` in each A/B root filesystem slot. This ensures that an OTA update updates the kernel and DTB together. ([docs.mender.io][3])

In the current GRUB-based boot flow, U-Boot loads the GRUB EFI binary and passes a DTB that was loaded from the separate boot partition:

```text
bootefi ${loadaddr} - ${fdt_addr}
```

Because this boot partition is outside the Mender A/B root filesystem slots, the DTB can remain unchanged after a root filesystem OTA update. This can cause the updated kernel to boot with an older DTB.

CompuLab previously implemented a GRUB-based solution that loads the Linux DTB from the same Mender-selected location as the kernel. The implementation uses:

```text
devicetree ${mender_kernel_path}/${kernel_devicetree}
```

before loading the kernel from `${mender_kernel_path}`. ([GitHub][4])

For the BSP and Mender version currently under discussion, the equivalent logic does not appear to be enabled in the active GRUB configuration.

### Mender can be integrated using either of the following boot-selection approaches:

#### GRUB-based Mender integration

* U-Boot is not modified for Mender A/B boot selection.
* U-Boot loads the GRUB EFI binary.
* The Mender A/B boot-selection and rollback logic is implemented in the GRUB configuration.
* GRUB should load both the Linux kernel and its matching DTB from the selected A/B root filesystem slot.

#### U-Boot-based Mender integration

* The Mender A/B boot-selection and rollback logic is implemented in the U-Boot environment and boot scripts.
* U-Boot selects the active Mender root filesystem slot.
* U-Boot loads the Linux kernel and its matching DTB from that same slot.

Recent Mender integration supports selecting either the GRUB-based or traditional U-Boot-based approach. ([docs.mender.io][7])

CompuLab provides its U-Boot-based Mender integration in the `scarthgap-nxp-uboot` branch. ([GitHub][8])
